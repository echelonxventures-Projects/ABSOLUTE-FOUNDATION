## 1. Executive Determination

The scoped question named three surfaces (`engine/uckp/registry.py`, `engine/knowledge/`, `00-BOOK/tools/ukb.py`). Direct repository reads show the real landscape is larger: `engine/knowledge/` is not one surface but **three layered subsystems** (UKDA, UKI, UKIP), and the document-corpus side has its own second implementation (`engine/graph/`, UCOS-EPIC-002) sitting alongside `ukb.py`. Eight surfaces in total were traced to a producer and a bounded purpose; none is orphaned or unexplained.

**Finding, in one sentence:** the landscape is overwhelmingly (B) valid, correctly-layered specialization that already reuses code properly — UKI and UKIP both import and compose UKDA's store/model/cko directly rather than reimplementing it — with exactly **one real, unaddressed governance gap**: `engine/uckp/registry.py` self-names itself "the Universal Knowledge Registry" and governs a genuinely different axis (general constitutional-object identity/admission) than `engine/knowledge/*`'s curated institutional/architectural knowledge, using an entirely separate, non-cross-referenced identity mechanism. This is the same shape of naming collision Phase 0.6 (CMG↔UCKP) and the Certification governance work each resolved this session — but it has never been named or recorded anywhere in this repository until this determination.

A second, much smaller gap exists: `engine/knowledge/ukip/certification.py` (UKIP Part 12) is not registered in the existing `certification_authority_resolution` binding, while its sibling `engine/knowledge/certification.py` (UKDA) already is.

## 4. Authority Analysis

- **UCKP Layer Zero (`engine/uckp/registry.py` + `ucko.py`)** claims to be the substrate for "the only thing in UCOS Ω∞ that holds authority." It governs Articles 2, 3, 8, 18 — universal object admission generally, of which knowledge content is only one possible governed category. It has **zero imports from `engine.knowledge`** (confirmed by grep across `registry.py`, `ucko.py`) and is the substrate this session's earlier CAA/identity/dependency-graph work (`id-ledger.json`, 5,804 identifiers, 32,937+ relationship edges) already sits on.
- **UKDA (`engine/knowledge/`)** is the declared authority for curated, authored-once institutional/architectural *decision* knowledge specifically — a narrower, content-specific domain than UCKO's universal object admission.
- **UKI and UKIP hold no independent authority.** UKI's own docstring states integration is "additive ... not feature expansion." UKIP composes directly with UKDA's store/cko/model (confirmed imports) rather than defining a parallel one. Both are properly-scoped extension layers of UKDA, not separate authorities.
- **UKB (`ukb.py`) explicitly disclaims authority in its own header**: "holds no constituent, governance, ratification, or EC-1 authority." This matches the disclaiming-authority pattern (`"NONE"` prefix) already recognized elsewhere in the CAA binding for other engineering-execution-only tools.
- **`engine/graph/` (EPIC-002)** explicitly declares itself a **projection**, not an authority, and cites an already-existing governance precedent for this exact question (UMB-006 "three roots, one graph"; GOV-INT-001) — this domain is **already reconciled**, just for the document-corpus axis rather than the knowledge-content axis this discovery was scoped to.

No surface in this landscape claims `SUPREME` under `AUTHORITY_ROLES` (`engine/uckp/alignment.py`) and none was found attempting to. The unresolved question is not "who is supreme" but "does 'Knowledge Registry' name one axis or two," which the existing CAA binding has never been asked to answer.

## 6. Gap Classification

1. **(C) Governance gap — primary finding.** `engine/uckp/registry.py` and `engine/knowledge/*` both use "Knowledge Registry"/"knowledge" as their name for genuinely different axes (general constitutional-object admission vs. curated institutional-knowledge content), with two separate, non-cross-referenced identity mechanisms (UCKO urn-identity vs. content-hash knowledge-identity). This is the exact shape of gap the CMG↔UCKP reconciliation (Phase 0.6) and the Certification governance binding both resolved this session — a real, non-competing specialization that simply lacks a recorded declaration.
2. **(D) Taxonomy gap — minor.** UKI's `DiscoveryProtocol` and UKIP's `KnowledgeDiscovery` share a name for related-but-distinct bounded questions (pre-creation duplicate check vs. post-admission findability) with no recorded distinction.
3. **Incomplete registration — minor, mechanical.** UKIP's `certification.py` (Part 12) is missing from the existing `certification_authority_resolution.surfaces` list that already carries its UKDA sibling.

No gap in this landscape rises to (A) true duplication. This matches the dominant pattern established across every reconciliation performed this session: apparent fragmentation in UCOS is almost always valid, already-correctly-layered specialization that was simply never declared.

Not implemented in this determination, per scope. For a future, separately-approved binding pass, the evidence above points to the same reusable mechanism already used three times this session (`identity_authority_resolution`, `relationship_graph_resolution`, `certification_authority_resolution` — each a `*_resolution` top-level section in `00-BOOK/DATA/constitutional-authority-alignment.json`):

   - `engine/knowledge/store.py` (UKDA) as the one authority over curated institutional/architectural knowledge content, with UKI and UKIP recorded as its integration and admission layers respectively (not separate authorities) — mirroring the "one authority, multiple planes" shape `identity_authority_resolution` already uses.
   - `engine/uckp/registry.py` as governing a distinct, orthogonal axis (general constitutional-object identity/admission, Articles 2/3/8/18) — resolving the naming collision by declaration, exactly as `ORTHOGONAL` resolved CMG↔UCKP in Phase 0.6.
   - The document-corpus axis (`ukb.py`, `engine/graph`) as out of scope for this binding, already governed by UMB-006/GOV-INT-001.
2. **Add one entry** to the existing `certification_authority_resolution.surfaces` array for `engine/knowledge/ukip/certification.py`, closing the incomplete-registration gap with the same mechanism already used for its UKDA sibling — no new section required for this part.
3. **Optionally record** the `DiscoveryProtocol`/`KnowledgeDiscovery` naming distinction in prose (not a new binding mechanism) if a future pass wants to close the (D) gap; this is the lowest-priority item found and carries no functional risk today.

This determination does not decide whether a knowledge-content identity scheme should eventually cross-reference UCKO identity — that is a design question for whoever implements item 1, not something repository evidence alone can settle.
