## OUTPUT 1 — APPLICATION PROGRAM DEFINITION

### 1.1 The APPLICATION domain

> **Application** in UCOS Ω∞ is the architecture of **composed, actor-facing capability delivery** — how contracted, invocable service operations are **assembled into modules, features, workflows, and interactions** that deliver capability to actors within bounded application contexts and states. Application is the third domain-realization layer (PHASE-006): founded upon existence (EL-1), behavior (RL-F2), composition (PL-F2), representation (DF-2), and operation (SF-2), it adds the concern of **what is delivered to an actor as a coherent, contextual, stateful whole**, redefining none of the layers below.

**Layering thesis (canonical; to be carried through APPLICATION-001…005):** Engineering = *existence*; Runtime = *behavior-over-existence*; Platform = *composition-over-behavior*; Data = *representation-over-composition*; Service = *operation-over-representation*; **Application = experience-over-operation** (the composed, contextual, stateful delivery of capability to an actor by assembling contracted operations into modules, features, workflows, and interactions). Application never redefines existence, behavior, composition, representation, or operation; it composes, contextualizes, sequences, and presents operations across them. The **experience** composition construct fixed by PLATFORM-009 is reused **by reference** and elaborated — never re-founded — into a full realization layer.

### 1.2 Domain vocabulary (to be fixed by APPLICATION-001…005; defined here only to scope the program)

| Term | Establishment meaning (implementation-independent) |
|------|----------------------------------------------------|
| **Application** | A bounded, named, actor-facing composition of modules/features that delivers a coherent set of capabilities within a context (reuses PLATFORM-009 experience composition by reference); the unit of delivered capability. |
| **Module** | A cohesive, bounded grouping of features within an application; the structural unit of application composition. |
| **Feature** | A discrete, named unit of actor-facing capability delivered by composing one or more service operations under contract. |
| **Capability** | An implementation-independent *ability delivered to an actor* (reuses PLATFORM-006 / SERVICE capability by reference); the "what is delivered". |
| **Use Case** | An implementation-independent goal-oriented interaction between an actor and the application that yields an outcome. |
| **Workflow** | An ordered, conditional arrangement of features/operations toward an outcome (reuses the RL-F2 / SERVICE workflow concern by reference). |
| **Journey** | The end-to-end path an actor traverses across features/workflows toward a goal (an evaluative composition of interactions and states). |
| **Screen** | An implementation-independent unit of presentation surface through which interaction occurs (the *abstract* surface; no rendering technology selected here). |
| **Interaction** | A defined actor-to-application exchange (input, command, query, response) at a boundary; the imperative act of engagement. |
| **State** | The implementation-independent condition of an application/module/feature/interaction at a point in a journey (reuses the RL-F2 state concern by reference). |
| **Process** | An orchestrated, possibly long-running arrangement of workflows/operations advancing application state toward an outcome. |
| **Context** | The bounded set of conditions (actor, session, tenant, locale, policy) under which an application operates. |
| **Boundary** | The explicit line delimiting what an application/module owns, exposes, composes, and depends upon. |
| **Composition** | Structural assembly of features into modules and modules into applications (reuses PLATFORM composition by reference). |
| **Application Lifecycle** | The implementation-independent lifecycle of an application (defined → composed → contextualized → executable → deprecated → retired) as an evaluative/architectural concept. |
| **Application Dependency** | A declared reliance of one application/module/feature upon another or upon a service operation (downward-only, acyclic within the program). |
