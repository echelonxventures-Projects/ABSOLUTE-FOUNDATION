## OUTPUT 3 — INFRASTRUCTURE DEFINITION

### 3.1 What Infrastructure means inside UCOS Ω∞

> **Infrastructure** in UCOS Ω∞ is the implementation-independent architecture of the **hosting, provisioning, topological, and delivery substrate** — how compute, network, storage-hosting, environments, topology, distribution, resilience, scaling, and delivery are architected (as concepts, not technologies) so that the composed application/service/data/platform/runtime/existence layers can be hosted, located, distributed, scaled, and delivered within bounded, isolated environments. Infrastructure is the realization-environment layer (PHASE-007): founded upon experience (AF-3), operation (SF-2), representation (DF-2), composition (PL-F2), behavior (RL-F2), and existence (EL-1), it adds the concern of **where and how the whole is hosted and delivered**, redefining none of the layers below.

### 3.2 Domain vocabulary (to be fixed by INFRASTRUCTURE-001…005; scoping definitions only)

| Term | Establishment meaning (implementation-independent) |
|------|----------------------------------------------------|
| **Environment** | A bounded, named substrate context (e.g. abstract dev/test/stage/prod-class) in which UCOS constructs are hosted; the unit of hosting context. |
| **Node** | An implementation-independent unit of hosting capacity to which constructs are placed. |
| **Cluster** | A cohesive grouping of nodes forming a hosting boundary. |
| **Topology** | The implementation-independent arrangement of environments/nodes/clusters and their connectivity and locality. |
| **Region / Zone / Location** | Abstract locality constructs describing where hosting occurs (no provider region selected). |
| **Compute Substrate** | The implementation-independent abstraction of execution-hosting capacity (never redefining RL-F2 execution). |
| **Network Substrate** | The implementation-independent abstraction of connectivity between hosted constructs. |
| **Storage Hosting** | The implementation-independent abstraction of *where* represented data (DF-2) is hosted/located — never the data representation itself. |
| **Provisioning** | The implementation-independent lifecycle of bringing infrastructure resources into and out of existence (defined → provisioned → active → decommissioned) as an architectural concept. |
| **Distribution / Delivery** | The implementation-independent arrangement by which hosted capability is distributed and delivered to actors/consumers. |
| **Resource / Capacity** | An implementation-independent quantum of hosting capability and its bounded amount. |
| **Scaling Substrate** | The implementation-independent abstraction of expanding/contracting capacity (aligned with AUTH-INF-001 infinite-scale as architecture, not as a hard ceiling). |
| **Availability / Resilience** | The implementation-independent architecture of continuity and fault-tolerance topology. |
| **Isolation / Boundary** | The explicit line delimiting what an environment owns, exposes, hosts, and isolates. |
| **Infrastructure Dependency** | A declared reliance of one infrastructure construct upon another or upon a hosted layer (downward-only, acyclic). |

These are **scoping definitions only**; normative fixation is deferred to INFRASTRUCTURE-001 (Constitution) through INFRASTRUCTURE-005 (Meta-Model).

### 3.3 What Infrastructure governs / does not govern
