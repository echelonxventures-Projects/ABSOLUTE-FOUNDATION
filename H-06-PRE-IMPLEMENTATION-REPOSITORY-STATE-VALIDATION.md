## 4. Commit Boundary Recommendation

### 4.1 Should H-06 Planning Documents Be Committed Separately?

**YES — as a single documentation-only commit, before any implementation commit.**

Rationale:

1. **Rollback isolation.** CIEP §5.2 requires every implementation change to be
   independently `git revert`-able. Reverting an implementation commit must not remove
   the governance record that authorized it. Planning documents and implementation
   changes therefore cannot share a commit.
2. **Evidence precedence.** CIEP §5.1 requires the baseline evidence snapshot to be
   stored "in the repository root as a dated artifact" *before* Phase 1 begins.
   An uncommitted Task-001 report is not preserved evidence — it is a working-tree file
   with no immutable reference.
3. **Zero-risk content.** All 33 H-06 documents are Markdown. None is executable, none is
   read by any gate, none is a declaration or registry. Committing them cannot alter gate
   behaviour or dirty derived truth.
4. **Traceability.** Commit messages for the implementation commits must reference IAR
   sections and GP findings (CIEP §5.1). Those references resolve only if the referenced
   documents are already in history.

**Scope of the recommended commit — exactly these, nothing else:**

- the 33 `H-06-*.md` documents
- `GATE-PURITY-DETERMINATION.md` (the finding source the whole chain cites)

**Excluded from it:** the 16 `PHASE-UCF-*.md`, the 17 other determination documents, and
the 3 untracked programme directories. These belong to other lineages and must not be
absorbed into an H-06 commit boundary.

**Excluded absolutely:** `H-06-MUTATION-GOVERNANCE-OWNER-DECISION-RECORD.md.save`
(see §4.3).
