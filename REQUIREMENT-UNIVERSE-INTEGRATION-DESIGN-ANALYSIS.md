**Net: requirement evolution is unowned.** Nothing in the repository owns the event "a new requirement arrived."

## 4. Implementation impact

**The integration cannot begin with an engine.** It must begin with a population decision, because every downstream stage inherits the ambiguity. Concretely:

1. **Resolve the population question (RU-G-01, RU-G-02).** Either the 49 and the 549 are one population with two views — in which case one is authoritative and the other is a **declared projection whose count is derived, not written** — or they are two populations with different subjects, in which case that must be stated so `UFC-16` is visibly satisfied rather than accidentally unbreached. **Reserved to a governing authority under `CEP-002` 14.2.**
2. **Give plane A an intake rule or retire it (RU-G-06).** A hand-tallied session-bounded index cannot receive discovered requirements. If it remains, it needs an admission grammar; if the 549-plane is authoritative, the index becomes a rendered view.
3. **Add normalization before detection (RU-G-03).** Duplicate and conflict detection are unsound without it. `requirements.json` already carries `content`-adjacent structure and the CKO plane already proves duplicate detection by hash equality (`PR-02`, Knowledge Once) — the mechanism exists; it has not been applied to requirements.
4. **Extend `EVOLUTION-001`, do not duplicate it (RU-G-05).** It is the only implemented intake lifecycle. Adding a ninth evolution class — *requirement admission* — is a smaller and more defensible act than a new engine, and it inherits the existing wave entry/exit criteria and baseline-protection rules.
5. **Defer the plan edge to the MIP determination (RU-G-04).** There is nothing to write to yet; see the companion Master Implementation Plan Evolution Proposal.

**What this determination explicitly does not do:** it does not choose between the planes. Doing so would breach the reservation that `UCOS-URR-001`'s disposition records, and would repeat the error that determination was written to prevent.

## 5. Validation approach

| Obligation | Measurement |
|---|---|
| One population, one measurement | Exactly one surface writes a requirement count; every other surface derives it. A check compares the derived count against the authoritative one and fails on divergence. |
| No second register | A check asserts no requirement-bearing artifact exists outside the declared authoritative path. |
| Normalization is deterministic | The same requirement text yields the same normal form and the same content hash across runs, with no clock and no locale dependence. |
| Duplicate detection is sound | Hash equality over normal forms, exactly as `PR-02` already does for knowledge objects. |
| Conflict detection is real | Each declared conflict names both subjects and a resolution disposition; an unresolved conflict blocks, and is never defaulted. |
| Ownership is declared, not inferred | `RG-B01` count (currently 406) is the measured metric; the acceptance target is a declared reduction with the remainder disclosed. |
| Intake is exercisable | Admit a synthetic requirement into a **copy** of the register each run and prove the original population did not move — the `ISD-L-11` admission-exercise pattern. |
| Population growth does not break tests | No test asserts 49 or 549 unless cardinality is itself the invariant. |

## 7. Acceptance criteria

1. Exactly one requirement population is declared authoritative, and every other requirement-bearing surface declares itself a projection whose count is **derived**. **Currently: two populations, no declaration.**
2. The 541 / 549 discrepancy is explained or corrected. **Currently unexplained.**
3. A discovered requirement can enter the authoritative population through a named, exercisable admission path, and the path is exercised on a copy each run.
4. Normalization is a pure deterministic function; identical input yields identical normal form and hash across runs.
5. Every declared conflict names both subjects and carries a resolution disposition. No conflict is silently defaulted.
6. `RG-B01 CANONICAL-OWNERSHIP-INFERRED` is reduced against a declared target, with the remainder disclosed as a gap. **Currently 406 of 549.**
7. No second requirement register, engine, gate or identifier scheme is created. `urr_engine.py` remains absent unless a governing authority admits `UCOS-URR-001`.
8. Index, traceability matrix and gap register report identical status for every shared identifier, or the non-authoritative ones are withdrawn. **Currently they disagree on at least seven.**
9. No requirement-completeness or certification claim is made while `requirements.json` reports `ASSIMILATION-INCOMPLETE`.
10. The two genuinely open items — `REQ-28` (192-document corpus registration, blocked on a `CEP-002` Article 28 decision, **not** on code) and `REQ-43` (`KnowledgeStore` storage-technology interface, assessed and **not recommended** in the openness roadmap Phase 3) — retain their existing dispositions. Neither is reopened by this work.

## 9. Determination

**THE ENGINE MUST NOT BE BUILT YET — THE POPULATION QUESTION IS PRIOR AND IS RESERVED.**

The directive's diagnosis is sound: existing requirements are being treated as a permanent limit rather than an initial discovered population, and there is no path by which a newly discovered requirement becomes governed work. Plane A cannot receive one at all.

But the remedy the directive proposes has already been attempted and refused on constitutional grounds, and the refusal was correct. Building a requirement evolution engine now would create a third requirement plane on top of two that already disagree — and the specific failure mode `UFC-16` names is exactly that. The prior condition is a **population decision**, and that decision is expressly reserved to a governing authority.

The reusable path, once the reservation is discharged, is narrow: normalization as a deterministic function, duplicate detection by the hash-equality mechanism that already serves knowledge objects, and admission as a ninth class in the one intake lifecycle the repository has actually implemented.

**VERDICT: `DETERMINATION-COMPLETE · BLOCKED-ON-RESERVED-DECISION · IMPLEMENTATION-NOT-AUTHORIZED`**

No register created, no requirement admitted, no population converged. Working tree unchanged.
