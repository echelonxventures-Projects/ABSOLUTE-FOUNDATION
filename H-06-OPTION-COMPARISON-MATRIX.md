| Dimension | Option A — Pure Observation Gate | Option B — Explicit Multi-Mode Gate | Shared Requirement |
|---|---|---|---|
| **1. Constitutional simplicity** | Highest: one rule — `*-gate` = write-free. No per-engine classification needed; rule is universal and self-enforcing by name. | Moderate: three valid modes, each with invariants. Correct classification requires per-engine judgment at declaration time. | Both require OBSERVE_WITH_DECLARED_AUDIT_EMISSION sub-classification for always-on audit writes (GP-5, GP-9 class). |
| **2. Evidence trust** | Highest ceiling: a gate that writes nothing cannot have altered what it measured. Evidence produced on an OBSERVE path is unconditionally trustworthy. | Moderate: PRODUCER gate evidence is trustworthy only if determinism and replay are verified. Without replay co-enforcement, the gate measures a state it simultaneously altered. OBSERVE gates retain highest ceiling. | Both require GP-2 write-order correction (3 engines) — a gate that writes before deciding cannot report a pre-write verdict under any mode. |
| **3. Implementation effort** | High: ≥18 engines must separate write from gate verdict in code before any declaration is truthful. ≥15 CI workflows require explicit render steps. | Lower: 11 declaration files require additive `gate_mode` field. Replay paths required per PRODUCER programme. Code changes limited to GP-2 (3 engines) and GP-10 (1 engine). | Both require GP-10 `aee-observe` emit() suppression (1 engine). Both require GP-5 label correction. |
| **4. Migration complexity** | High: gates remain in violation until code is changed. Derived truth never updates in CI until render steps are added. Migration window may be extended. Grandfathering policy required for the transition period. | Lower: PRODUCER declaration is additive and immediate. Engines continue current behaviour while replay contracts are implemented. Migration window shorter but replay co-obligation must not slip. | Both require a grandfathering policy for the migration window — 24 undeclared-mutation engines remain in violation until their path is complete. |
| **5. Future extensibility** | Simple: every new programme's gate is OBSERVE by definition. A write path must be separately named. New programmes cannot accidentally inherit mutation authority. | Flexible: a new programme declares its mode in its declaration. PRODUCER is available where generation is the genuine purpose. Requires discipline at declaration time to prevent mode inflation. | Both require the `--check-declaration` self-guard to enforce declared mode at runtime — already present in each engine. |
| **6. Operational safety** | Highest: running any `*-gate` target is unconditionally safe. The F-A irreversible-loss event (FINAL-FREEZE-ELIGIBILITY-DETERMINATION.md §1.1) cannot recur under this model. | Moderate: OBSERVE-declared gates are safe. PRODUCER and EXECUTION gates mutate by design. An operator must know the mode before running. The F-A class event remains possible on PRODUCER paths if run outside intended context. | Both eliminate undeclared mutation as a class once mode declarations are in place and enforced. |
| **7. Freeze acceleration** | Slower initial path: freeze conditions cannot be satisfied until code changes in ≥18 engines are complete. Timeline depends on implementation authorization and execution. | Faster initial path: declaration changes alone advance the mutation-boundaries condition. Replay co-obligation is the rate-limiting step; code change scope is smaller. | Both satisfy the same three freeze conditions (mutation boundaries declared, replay integrity proven, evidence chain trustworthy) — the difference is how many steps lie between the H-06 decision and those conditions being met. |
| **8. Governance clarity** | Unambiguous: mode is determined by naming convention. `*-gate` = OBSERVE; `*-render`/`*-run` = PRODUCER/EXECUTION. No judgment required at declaration time. | Requires judgment: a programme author must classify their gate path correctly. Decision criteria (what qualifies as PRODUCER) must be defined and enforced. Mode inflation is a governance risk without clear qualifying criteria. | Both require explicit criteria for OBSERVE_WITH_DECLARED_AUDIT_EMISSION to prevent every audit write from claiming special status. |
| **9. Risk containment** | Stronger structural containment: the invariant is enforced by gate/render separation at the code level, not by declaration discipline. A gate that writes is detectable without reading any declaration. | Declaration-dependent: containment relies on accurate mode declarations and the self-guard enforcing them. A false declaration or an unenforced guard leaves undeclared mutation possible. Requires active enforcement. | Both rely on `forbidden_write_prefixes` for write-scope containment — existing, tested, currently enforced. |
| **10. Long-term maintainability** | Lower ongoing cost: the naming convention is self-documenting. New contributors cannot accidentally add writes to a gate path without violating a named invariant. | Higher ongoing cost: mode declarations must be kept accurate as engines evolve. A PRODUCER engine that gains an OBSERVE alias (like `aee-observe`) must maintain the alias's write suppression separately. Requires per-change discipline. | Both require replay paths to be maintained as engines evolve — a replay that passes today can fail after a schema change if not re-verified. |
