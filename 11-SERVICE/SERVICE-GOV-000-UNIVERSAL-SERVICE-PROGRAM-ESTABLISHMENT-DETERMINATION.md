## OUTPUT 1 — SERVICE PROGRAM DEFINITION

### 1.1 The SERVICE domain

> **Service** in UCOS Ω∞ is the architecture of **invocable, contracted operation** — how identified, typed, valued, related, behaving, composed, and represented constructs are **exposed, invoked, orchestrated, and executed under explicit contracts and policy** to perform work. Service is the second domain-realization layer (PHASE-005): founded upon existence (EL-1), behavior (RL-F2), composition (PL-F2), and representation (DF-2), it adds the concern of **what can be requested, performed, and delivered**, redefining none of the layers below.

**Layering thesis (canonical; to be carried through SERVICE-001…005):** Engineering = *existence*; Runtime = *behavior-over-existence*; Platform = *composition-over-behavior*; Data = *representation-over-composition*; **Service = operation-over-representation** (the contracted, invocable action by which composed, behaving, represented constructs deliver capability). Service never redefines existence, behavior, composition, or representation; it exposes, contracts, orchestrates, and executes operations across them. The **service** composition construct fixed by PLATFORM-008 is reused **by reference** and elaborated — never re-founded — into a full realization layer.

### 1.2 Domain vocabulary (to be fixed by SERVICE-001…005; defined here only to scope the program)

| Term | Establishment meaning (implementation-independent) |
|------|----------------------------------------------------|
| **Capability** | An implementation-independent *ability to perform work* (reuses PLATFORM-006 capability by reference); the "what can be done". |
| **Service** | A bounded, named, contracted provider of one or more operations (reuses PLATFORM-008 service composition by reference); the unit of exposed capability. |
| **Operation** | A single, named, invocable unit of work exposed by a service, with typed inputs/outputs and defined effects. |
| **Action** | The performance of an operation — the imperative act that changes or reads state (behavior by reference to RL-F2). |
| **Command** | A request to perform an action that intends a state change (write-side operation). |
| **Event** | A represented occurrence emitted by a service (reuses the RUNTIME event concern + DATA event data by reference). |
| **Contract** | The binding, implementation-independent specification of an operation/service: inputs, outputs, effects, pre/post-conditions, faults, policy. |
| **Interface** | The typed surface through which a service's operations are addressed (the shape; distinct from the endpoint that locates it). |
| **Endpoint** | An addressable point at which an interface is made available (abstract locus; no protocol/transport selected here). |
| **Workflow** | An ordered, conditional arrangement of operations toward an outcome (reuses the RUNTIME workflow concern by reference). |
| **Orchestration** | Centrally coordinated composition of multiple services/operations toward a goal (a coordinator drives). |
| **Composition** | Structural assembly of services/operations into larger services (reuses PLATFORM composition by reference). |
| **Execution** | The runtime carrying-out of an invoked operation (binds to RL-F2 behavior by reference). |
| **Transaction** | A bounded unit of execution with atomicity/consistency semantics over represented state (reuses RUNTIME state + DATA lifecycle by reference). |
| **State Transition** | A defined change of service/operation state driven by an action (reuses the RUNTIME state concern by reference). |
| **Policy Enforcement** | The application of governing rules (authz, quota, validation, SLA) at contract/operation boundaries (reuses the RUNTIME policy concern by reference). |
| **Service Boundary** | The explicit line delimiting what a service owns, exposes, and depends upon. |
| **Service Dependency** | A declared reliance of one service/operation upon another (downward-only, acyclic within the program). |
| **Service Lifecycle** | The implementation-independent lifecycle of a service (defined → contracted → composed → executable → deprecated → retired) as an evaluative/architectural concept. |

These are **scoping definitions only**; their normative fixation is deferred to SERVICE-001 (Constitution) through SERVICE-005 (Meta-Model).
